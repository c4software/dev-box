iPhone and iPad apps: what is left after devbox dev-env ios

  1. The Apple account and the iOS SDK, once
     Download Xcode from https://developer.apple.com/download/all/?q=Xcode in
     a browser (the page asks for an Apple ID, a free one will do, and the
     file weighs several GB). Take the Xcode that carries the Swift of the
     box (`swift --version`): Xcode 27 for Swift 6.4, Xcode 26 for Swift 6.3.
     Put the .xip in the home of the box: ./data/home on the host, or scp.
     Then, in the box, all of this step in one go:
       devbox ios            pick the .xip, build the SDK, sign in
       devbox ios status     SDK registered, Apple signed in
       devbox ios login      the sign-in alone, again (devbox ios logout)
     It builds the SDK from the .xip through install-toolchain.sh, keeps it
     in ~/.cache/xtool (the .xip can go once it is there), registers it and
     adds the macros and the tools the SDK of xtool lacks, then signs in to
     Apple. Sign-in skipped or failed: devbox ios login (devbox ios logout
     first to change account or after a wrong code).
     Mode 0, an App Store Connect API key, with a paid Apple Developer
     Program membership: devbox ios xcode over USB and Wi-Fi. Mode 1, the
     password, with any Apple ID, a free one will do (email, password, the
     two-factor code): over USB only, and the signature of a free account
     lasts 7 days. It goes through private Apple APIs, hence the throwaway
     Apple ID xtool suggests.
     Without an Xcode download, experimental (Objective-C, C, Swift and a
     small part of SwiftUI, read sdk-free/README.md of the clone first):
       install-toolchain.sh --mode no-xcode

  2. On the host, then in the box: the device, once
     The device is on your desk and the box on a remote machine: skip this
     step for `devbox help ios-usb`. Plugged into the machine that runs the
     box: Docker gives the box no USB device by default. On that host, add
     to compose.override.yaml, next to compose.yaml (cp
     compose.override.example.yaml compose.override.yaml the first time):
       services:
         dev-box:
           volumes:
             - /dev/bus/usb:/dev/bus/usb
           device_cgroup_rules:
             - 'c 189:* rmw'
     The bus as a volume, so a device plugged in later shows up too, and the
     rule that lets the box open it. A volumes or device_cgroup_rules key
     there already: add the line to it, a second one is refused. The usbmuxd
     of the host lets go of the device (udev starts it again at each plug):
       sudo systemctl mask --now usbmuxd    unmask it to give it back
       docker compose up -d
     In the box:
       devbox pkg add usbmuxd
     Plug the iPhone or iPad in, unlock it, then:
       devbox ios devices    answer Trust on the device, then run it again
     It starts the usbmuxd of the box when it is not running, as every
     command that reaches the device does.
     usbmuxd keeps its pairing records in /var/lib/lockdown, outside the
     home: expect Trust again after a rebuild of the box. Without the
     cable afterwards, on iOS 27: `devbox help ios-wifi`.

  3. A first app
     A directory with the Swift sources in Sources/ and, next to them, a
     project.yml for XcodeGen (devbox ios xcode builds XcodeGen itself):
       name: Hello
       options:
         deploymentTarget:
           iOS: "17.0"
       targets:
         Hello:
           type: application
           platform: iOS
           sources:
             - Sources
           info:
             path: Sources/Info.plist
             properties:
               CFBundleDisplayName: Hello
               UILaunchScreen: {}
           settings:
             base:
               PRODUCT_BUNDLE_IDENTIFIER: fr.example.hello
     Sources/ holds the @main App of SwiftUI and its views; the bundle ID
     is yours, reversed domain style, unique across every Apple account.
     Then, in that directory:
       devbox ios xcode      builds, signs, installs and launches the app
     The first build takes a few minutes, the next ones are quick. On the
     device, if asked: Settings, Privacy & Security, Developer Mode (it
     restarts), then devbox ios xcode again. At the first launch of the
     app, on "Untrusted Developer": Settings, General, VPN & Device
     Management, your Apple ID, Trust. With a free account the signature
     lasts 7 days: devbox ios xcode again renews it. From the host, for a
     project mounted from it: scripts/devbox-build.sh of the repository of
     dev-box, put next to project.yml.

  4. Around it
     In the directory of the app:
       devbox ios xcode build         builds without installing
       devbox ios xcode logs          the logs of the app
     In build/devbox-ios/xtool, the package devbox ios xcode writes:
       device-run.sh --lldb           installs, then debugs it on the device
       ship.sh                        an App Store .ipa, checked offline
       ship.sh --upload               the same, sent to TestFlight
       pymobiledevice3 syslog live    the logs of the device
       pymobiledevice3 crash pull ./crashes    its crash reports
     ship.sh --upload takes an App Store Connect API key (ASC_KEY_PATH,
     ASC_ISSUER_ID, ASC_KEY_ID) and the app created once in App Store
     Connect. Flutter apps: devbox dev-env flutter, devbox pkg add llvm, then
     flutter/README.md of the clone, ~/.local/share/omarchy-apple-dev.

  5. A newer Swift, later
     swift is pinned: devbox dev-env --remove swift, then devbox dev-env ios,
     which installs the newer one and gives lldb its Python again. Then:
       install-toolchain.sh --repair    registers the cached SDK again
     A build that then fails on stale modules: delete the .build of the
     project. A Swift of another minor version wants the SDK of its own
     Xcode:
       swift sdk remove darwin
       XCODE_XIP=~/Xcode_28.xip install-toolchain.sh

  A box that had ios before omarchy-apple-dev
     It still runs the xtool AppImage of mise, without the macros and the
     tools above. Move it over, once:
       devbox dev-env ios            builds xtool, a few minutes
       swift sdk list                darwin: the SDK of xtool setup is kept
     With darwin listed, install-toolchain.sh has already added the macros
     and the tools to it. Its cache is empty though, so --repair has nothing
     to register after a change of Swift: give the .xip once to fill it.
       devbox ios                    picks the .xip, fills the cache
     The Apple sign-in and the pairing records stay: no new sign-in, no
     Trust again.

  A newer omarchy-apple-dev
     The image pins its release. After an image update, devbox dev-env ios
     moves the clone to the new one and runs install-toolchain.sh again;
     devbox ios kmp and devbox ios xcode stop and ask for it until then
     (devbox ios status shows the release of the clone).
     pymobiledevice3 that no longer starts after python moved:
       install-toolchain.sh --repair

  A Kotlin Multiplatform app
     Gradle skips the iOS framework of a Kotlin Multiplatform project on
     Linux. devbox ios kmp links it from the klibs Gradle builds, through
     kmp/build-framework.sh of omarchy-apple-dev: the framework the project
     declares (binaries.framework), its exports and options, in
     <module>/build/omarchy-kmp/<target> (--xcframework wraps it too). It
     needs a JDK and the SDK of step 1. The first run takes about 300 MB
     from Maven Central.
       devbox dev-env java
       devbox ios kmp ~/projets/<app>             for a device (ios_arm64)
       devbox ios kmp --target ios_simulator_arm64
       devbox ios kmp --help
     The build is optimized, without debug info. Compose Multiplatform
     resources land in compose-resources/ next to it. The app around it:
     devbox ios xcode --kmp :module (An Xcode project, below) links the
     framework through this command, then builds, installs and launches the
     app. --dynamic when the project declares a static one, which swift
     build cannot link here (-all_load).
     A project mounted from the host with rootless Docker is written by
     root only: run it as root from the host, it takes the tools of the
     box's user. Android targets in the project: Gradle needs the Android
     SDK, mounted read-only where sdk.dir of local.properties points.
       docker exec -u 0:0 -w /home/dev/projets/<app> dev-box \
         devbox ios kmp . --dynamic                on the host

  An Xcode project
     devbox ios xcode builds the app of an .xcodeproj, or of an XcodeGen
     project.yml, on Linux, then signs it for the device plugged in,
     installs and launches it. It needs the
     SDK of step 1, xtool signed in and the device of step 2. Signed in
     with an App Store Connect API key, it signs through provision-dev.py
     and also reaches the device over Wi-Fi with --wifi (`devbox help
     ios-wifi`). Signed in with the password of an Apple ID, a free one
     included, xtool install signs and installs, over USB only: trust the
     developer once on the device, the signature lasts 7 days.
       cd ~/projets/<app>
       devbox ios xcode                  build, install, launch
       devbox ios xcode build            or project, install, launch, logs
       devbox ios xcode --configuration Release
       devbox ios xcode --package mylib=~/projets/mylib@main
       devbox ios xcode --kmp :shared    around a Kotlin Multiplatform
                                         framework (the app in iosApp/)
       devbox ios xcode --help           the options, what they change
     It leans on omarchy-apple-dev: xcodeproj2xtool.py reads the settings of
     one configuration (Debug by default) and writes the Color.name and
     UIColor(.name) shortcuts Xcode writes, host-manifests.py answers as on a
     Mac the manifests of direct dependencies that test the build machine
     (RxSwift drops RxCocoa on Linux), ship.sh --device builds (app icon,
     resources at the root of the .app, the app's Info.plist keys in its
     resource bundle). On its own it targets iOS 17 at least (the asset
     symbols of the box need it) and, with an API key, signs through
     provision-dev.py: the profile of xtool install holds the first 20
     devices of the team only.
     Run-script phases are not run: commit what they generate. A project
     mounted from the host with rootless Docker:
       docker exec -u 0:0 -w /home/dev/projets/<app> dev-box \
         devbox ios xcode .                        on the host
     The same from the host, without a shell in the box: put
     scripts/devbox-build.sh of the dev-box repository next to project.yml
     (or the .xcodeproj), then, in that directory of the host:
       ./devbox-build.sh                 build, install, launch
       ./devbox-build.sh run --wifi <address>
       ./devbox-build.sh --help          its steps and settings
       https://raw.githubusercontent.com/c4software/dev-box/main/scripts/devbox-build.sh
     It runs devbox ios xcode as root in the box already running, with the
     path of the project seen from the box, and checks the SDK and the
     Apple sign-in first; a Flutter project goes to flutter/build.sh.
     After moving to omarchy-apple-dev 0.4.4, the SDK is built once more
     from the .xip (step 1): the SDK of the older xtool is refused.
